# Codegen

Generates the data API SDKs of every platform from one description of each API:

| Platform | Target id | Output                                   | Built on                      |
|----------|-----------|------------------------------------------|-------------------------------|
| Android  | `kotlin`  | `android/data-api/<api>/src/main/kotlin` | Ktor, kotlinx.serialization   |
| iOS      | `swift`   | `ios/DataApi/Sources/<Api>/Generated`    | `URLSession`, `Codable`       |
| Web      | `web`     | `web/packages/<api>/src/generated`       | `fetch`, TypeScript           |

## Running

From this directory, with the Android Gradle wrapper:

```sh
../../android/gradlew :cli:run                                  # every API under ../specs
../../android/gradlew :cli:run --args="specs/esse3"             # one API (paths are relative to common/)
../../android/gradlew :cli:run --args="--target web specs/esse3"  # one target
../../android/gradlew :cli:run --args="--check"                 # fail if any generated file is out of date (CI)
```

Generated files start with a `Generated by MyBicocca codegen` header and must not be edited.
A run rewrites changed files and deletes generated files it no longer produces; hand-written
files next to them are never touched.

## How it works

```
specs/<api>/  ──reader──▶  ApiSpec (model)  ──validator──▶  target ──▶ files ──▶ output sync
```

| Module      | Role                                                                                       |
|-------------|--------------------------------------------------------------------------------------------|
| `model`     | The language-neutral description of an API: modules, records, enums, operations, codecs.  |
| `core`      | Plugin interfaces (`SpecReader`, `CodeTarget`), `CodeWriter`, config, output sync, pipeline. |
| `readers/*` | One per spec format. `esse3` reads the Swagger specs scraped from Esse3 plus its overlays; `openapi` reads hand-written OpenAPI 3.0 with the `x-mb-*` extensions listed in its `Extensions.kt` (used by Affluences). |
| `targets/*` | One per platform: `kotlin`, `swift`, `web`.                                                |
| `cli`       | The command line, wiring the plugins found on the classpath.                               |
| `testing`   | A sample API covering every model feature, and golden-file assertions.                     |

Each API's `specs/<api>/codegen.json` names its reader and the targets to run:

```json
{
  "reader": { "type": "esse3" },
  "targets": {
    "kotlin": { "outputDir": "../../../android/data-api/esse3/src/main/kotlin", "options": { "packageName": "…" } },
    "swift": { "outputDir": "../../../ios/DataApi/Sources/Esse3/Generated" },
    "web": { "outputDir": "../../../web/packages/esse3/src/generated" }
  }
}
```

### The model

Readers do all the API-specific work (translating names, merging enums, deciding defaults), so
targets only map the model to their language. Every name in the model is final: declarations
are PascalCase and members camelCase, and targets only escape reserved words.

Decoding follows what lenient servers need: a field's `default` applies when its key is missing
or unusable, and non-standard wire formats are named by a `Codec`. Operations can also target
one of several `servers`, unwrap their response from an `envelope` (`{"data": …}`), send fixed
`headers` and header parameters, and accept credentials from `authSchemes`, which targets turn
into one type per scheme so a caller can only pass one valid set. Codecs are a closed sealed
set, implemented once per language in the runtime, so adding one fails to compile in each
target until that target handles it.

### Runtimes

Generated code calls a small hand-written runtime per language, and per API:

- **Kotlin**: `<Prefix>AbstractApi` (request helpers), `<Prefix>Runtime` (JSON and HTTP client),
  `<Prefix>PermissionLevel` and the date serializers named in the target's options. See
  `KotlinLayout`.
- **Swift**: the `DataApiRuntime` module (`ios/DataApi/Sources/DataApiRuntime`) and
  `<Prefix>Client`. See `SwiftLayout`.
- **Web**: `@mybicocca/data-api-runtime` (`web/packages/runtime`) and the API's
  `client.ts`. See `TsLayout`.

## Extending

- **A new platform**: add a `targets/<id>` module with a `CodeTarget`, list it in
  `META-INF/services/it.attendance100.mybicocca.codegen.core.CodeTarget`, add it to
  `settings.gradle.kts` and as a `runtimeOnly` dependency of `cli`, then write its runtime.
  Nothing else changes. Start from an existing target: they share the same structure (layout,
  syntax, one emitter per declaration kind).
- **A new spec format**: the same with a `SpecReader` under `readers/<id>`.
- **A new codec**: add it to `Codec` in the model and implement it in every target and runtime.

## Testing

```sh
../../android/gradlew test                      # all modules
../../android/gradlew test -PupdateGolden=true  # rewrite the targets' golden files after an intended change
```

Each target renders the sample API of `testing` and compares it with the golden files in its
`src/test/golden`, so a change to a target's output shows up as a reviewable diff. CI also
type-checks the web SDKs and builds and tests the Swift package on macOS.
