# Codegen

Codegen writes the code our apps use to talk to the university's services. You describe an API
once in `common/specs`, and it generates a client for each platform:

| Platform | Target    | Package                          | Built on                    |
|----------|-----------|----------------------------------|-----------------------------|
| Android  | `kotlin`  | `android/data-api` (Gradle)      | Ktor, kotlinx.serialization |
| iOS      | `swift`   | `ios/DataApi` (Swift package)    | `URLSession`, `Codable`     |
| Web      | `web`     | `web/web-app/data-api` (npm package) | `fetch`, TypeScript         |

The three packages are laid out the same way. APIs of the same service are grouped together, and
each group is split into the API itself, its data types and its errors:

| Group        | Kotlin package | Swift module | TypeScript import                |
|--------------|----------------|--------------|----------------------------------|
| Esse3        | `esse3`        | `Esse3`      | `@mybicocca/data-api/esse3`      |
| E-learning   | `elearning`    | `Elearning`  | `@mybicocca/data-api/elearning`  |
| EasyStaff    | `easystaff`    | `EasyStaff`  | `@mybicocca/data-api/easystaff`  |
| Affluences   | `affluences`   | `Affluences` | `@mybicocca/data-api/affluences` |

| Inside a group | Kotlin      | Swift    | TypeScript |
|----------------|-------------|----------|------------|
| The API        | `api`       | `API`    | `api`      |
| Data types     | `dto`       | `Models` | `models`   |
| Errors         | `exception` | `Errors` | `errors`   |

Each API's `codegen.json` says which group it belongs to. Every source file in the packages is
generated, runtimes included, and so are their [live tests](#live-tests); only the build files
are written by hand. Generated files start with `Generated by MyBicocca codegen`. Don't edit them
by hand: change the spec and run the generator again.

## Running it

Run these from `common/codegen`, using the Android Gradle wrapper:

```sh
../../android/gradlew :cli:run                                    # every API
../../android/gradlew :cli:run --args="specs/esse3"               # one API
../../android/gradlew :cli:run --args="--target web specs/esse3"  # one API, one platform
../../android/gradlew :cli:run --args="--check"                   # only check nothing is out of date
../../android/gradlew :cli:run --args="--plan specs/esse3"        # list the live tests and what they skip
../../android/gradlew :cli:run --args="--resources specs/esse3"   # fetch its resources' data again (slow)
../../android/gradlew :cli:run --args="--help"                    # all the options
```

Spec paths are relative to `common/`. CI runs `--check`, so remember to regenerate and commit
after changing a spec.

A run updates the files that changed and deletes the ones it no longer produces. It never
touches hand-written files, and it stops with an error rather than overwrite one. Several APIs
can share an output folder safely, because each file's header says which API it belongs to.

Some files belong to no single API: the runtimes, and the web package's `index.ts` files. These
are a target's *shared files*, written once per output folder whatever APIs the run covers (see
`CodeTarget.sharedFiles` and `CodeTarget.indexFiles`). So regenerating just one API never
breaks the others.

## How it works

```
specs/<api>/  ──reader──▶  model  ──validator──▶  target  ──▶  files on disk
```

1. A **reader** turns a spec into the model, a description of the API that doesn't depend on
   any language.
2. The **validator** checks the model, so mistakes show up when generating rather than at
   runtime.
3. Each **target** turns the model into code for its platform.

The project is split into modules along the same lines:

| Module      | What it does                                                          |
|-------------|-----------------------------------------------------------------------|
| `model`     | The model: modules, records, enums, operations and so on               |
| `core`      | The plugin interfaces, config loading, the pipeline and file syncing  |
| `readers/*` | One per spec format (see below)                                       |
| `targets/*` | One per platform: `kotlin`, `swift`, `web`                            |
| `cli`       | The command line, built with [Clikt](https://github.com/ajalt/clikt)  |
| `testing`   | A sample API that uses every feature, plus golden-file helpers        |

There are three readers:

- `esse3` reads the Swagger specs published by Esse3, plus our fixes on top of them (a glossary
  of names, enum names, fields that are really required).
- `moodle` reads the list of Moodle web service functions, extracted from Moodle's source. See
  `specs/moodle`.
- `openapi` reads hand-written OpenAPI 3.0 files, with our own `x-mb-*` extensions (listed in
  its `Extensions.kt`). Affluences, the EasyStaff portals, Kaltura and the Moodle pages use it.

### Configuring an API

Each API has a `specs/<api>/codegen.json` that says which reader to use and where each target
writes:

```json
{
  "reader": { "type": "esse3" },
  "targets": {
    "kotlin": {
      "outputDir": "../../../android/data-api/src/main/kotlin",
      "testOutputDir": "../../../android/data-api/src/test/kotlin",
      "options": { "packageName": "…esse3" }
    },
    "swift": { "outputDir": "../../../ios/DataApi/Sources", "options": { "module": "Esse3" } },
    "web": { "outputDir": "../../../web/web-app/data-api/src", "options": { "packageName": "esse3" } }
  }
}
```

`testOutputDir` is where the target writes the API's live tests; there are none without it, or
without a `tests.yaml`. `resourceOutputDir` is where it writes the API's
[resources](#resources), when not next to the code: Kotlin's go in `src/main/resources`.

An API can also be described by more than one spec. Esse3 does this for the pages of its web
portal that the REST API doesn't cover:

```json
"readers": [
  { "type": "esse3" },
  { "type": "openapi", "options": { "spec": "web/certificates.yaml" } }
]
```

The parts become a single API with one entry point. They have to agree on the API's id, prefix
and parameters, and anything they both declare (an enum, a server) must be identical.

## What a spec can describe

The university's services are far from textbook REST, so the model covers a lot of quirks. The
readers deal with each API's oddities, such as translating Italian names or merging duplicate
enums, so the targets only have to map the model to their language. Names in the model are
final; targets only escape reserved words.

### Data

- **Lenient decoding.** A field's default kicks in when its key is missing or unusable. Numbers
  and booleans may arrive as strings, and booleans as `0`/`1`.
- **Odd formats.** A `Codec` names a non-standard encoding: custom date patterns, epoch seconds,
  blank strings meaning "no value", JSON inside a string, lists sent as one joined string,
  and so on.
- **Maps** can be keyed by dates, enums or records written as one string (like `09:00-09:30`),
  and accept PHP's `[]` for an empty map.
- **Enums** can have integer values.

Codecs are a closed set, implemented once in each runtime. Adding one breaks the build of every
target until it handles it, so none can be forgotten.

### Requests

- Operations can pick one of several servers and unwrap their response from an envelope such as
  `{"data": …}`.
- Parameters go in the path, query, headers, cookies or form, encoded as JSON or PHP-style
  (`ids[0]=1`, `sede[]=U6&sede[]=U7`) when needed.
- Bodies can be JSON, URL-encoded forms or multipart forms with files (the runtimes'
  `FileUpload`).
- Responses can be JSON, bytes, plain text (such as a video playlist), JSON assigned to a
  variable in a script (`var elenco_sedi = [...];`), or an HTML page (see Scraping).
- Credentials are declared as auth schemes, and each becomes its own type, so callers can only
  pass a valid set.
- API-wide parameters, like a portal id, are given once when creating the API.
- Every operation says what calling it does to the server's state: its effect (see
  [Live tests](#live-tests)).

### Clients

A spec also describes how its client behaves (the `x-mb-client` extension; Esse3 and Moodle keep
it in a `client.yaml`):

- the base URL, and the headers, query parameters and cookies every request carries;
- settings the caller can change, such as Moodle's language;
- where an error's code and message are, even for servers that report errors with HTTP 200;
- the error codes callers may want to handle, which become constants;
- which statuses just mean an empty list;
- which failures to retry, after a delay or after another request (such as fetching a fresh
  token).

### Scraping

Some data only exists as HTML pages. A record can be read from a page by giving each field a
*scrape*: a short list of steps from the record's element to the value. For example, to read a
room's capacity from `<span class="custom-color-bold">Capacità</span>120 posti`:

```yaml
capacity:
  type: integer
  x-mb-scrape:
    - select-all: .custom-color-bold
    - where: [text, { equals: Capacità }]
    - first
    - last-sibling
    - text
    - remove-suffix: " posti"
```

The steps can:

- **navigate**: `select`, `select-all`, `next`, `last-sibling`, `follow`, `sections`, `where`,
  `first`;
- **read**: `text`, `own-text`, `html`, `attribute`, `url`, `lines`, `exists`;
- **transform text**: `regex`, `remove-prefix`, `unwrap`, `null-if`, `query-parameter`,
  `replace`;
- **test text**: `equals`, `contains`, `not`.

`first-of` tries several alternatives and takes the first that finds something. If a value is
missing, the field's default applies; a record missing a required value is dropped from its
list.

Each target compiles the steps to native code for its HTML parser (Jsoup, SwiftSoup or the
browser's DOM). The validator checks every step gets the kind of input it expects, and selectors
are limited to the CSS all three parsers support. New steps are added only when a page needs
them.

## Resources

Besides code, an SDK can ship data: the catalog of the e-learning courses, the students' ratings
of each course. A spec declares each resource and its type, built from ordinary schemas:

```yaml
x-mb-resources:
  catalog:
    type: MoodleWebCatalog        # a record the data decodes as
    builder: elearning-catalog    # what fetches the data again
    description: The courses on the university's Moodle.
```

The data lives next to the spec, in `specs/<api>/resources/<name>.json`, and generating never
touches the network: every target writes the same minified JSON into its platform's resources,
with a typed loader.

| Platform   | Data                                                  | Loader                                |
|------------|-------------------------------------------------------|---------------------------------------|
| Kotlin     | `src/main/resources/<package>/api/<api>/<name>.json`  | `MoodleWebResources.catalog()`        |
| Swift      | `Sources/<Module>/Resources/<api>/<name>.json`, copied into the module's bundle | `try MoodleWebResources.catalog()` |
| TypeScript | `src/<package>/resources/<api>/<name>.json`, imported on demand | `await MoodleWebResources.catalog()` |

A loader decodes the data on every call, so callers keep the result. JSON has no comments, so the
files carry their generated marker as their first key, `_generated`, which decoders ignore.

`--resources` fetches the data again with each resource's builder, checks it against its type and
saves it, before generating as usual. The builders, in `resources/`, crawl websites:

| Builder             | Data                                                                   | Takes |
|---------------------|------------------------------------------------------------------------|-------|
| `elearning-catalog` | Every category and course on elearning.unimib.it                       | Minutes |
| `course-ratings`    | The students' ratings of every course and teacher on opinionistudenti.unimib.it, by academic year | Hours the first time, and a run that stops keeps the years it finished; then only the site's last two years are fetched again. Every page is checked against the questionnaire counts of the page that led to it and tried again on the site's other servers. The site leaves some study courses and courses out of their listings for good: once every year is fetched, they are looked for among the codes of every year and the gaps in their numbering, and taken when they make up what the listing lacks exactly. Questionnaires the site attributes to none of a course's teachers are kept as its `unattributed_questionnaires`; anything else that never comes whole is kept as served and listed in its year's `gaps`, which later runs fetch again. It sends each of the site's servers one request at a time, and leaves one that slows down alone for a couple of minutes |

The `Resources` workflow runs `--resources` every week and opens a pull request when the data
changed.

## Runtimes

Generated code sits on a small runtime for each language: sending requests, handling errors and
retries, lenient decoding, dates and scraping. The runtimes are written by hand, but they live in
the generator, as resources of each target, and the targets copy them into the packages:

| Language   | Source in `targets/`              | Ends up in                                 |
|------------|-----------------------------------|--------------------------------------------|
| Kotlin     | `kotlin/src/main/resources/kotlin-runtime` | the `runtime` package of `android/data-api` |
| Swift      | `swift/src/main/resources/swift-runtime`   | the `DataApiRuntime` module of `ios/DataApi` |
| TypeScript | `web/src/main/resources/web-runtime`       | `web/web-app/data-api/src/runtime`         |

To change a runtime, edit it here and regenerate. The Swift runtime's tests stay in
`ios/DataApi/Tests` and run against the copy.

On top of the runtime, each API gets its own client and an error type with a constant for each
error code. Each target's `Layout` class lists exactly which files it writes.

## Live tests

Next to each SDK, the generator writes tests that call the real services with a test account:
JUnit for Kotlin, XCTest for Swift and vitest for TypeScript. All three run the same cases,
worked out once from the API's spec and its `tests.yaml` by the `TestPlanner`. They check that:

- **every read works**, called with every pair of parameter values tried at least once: each
  enum value, both booleans, optional parameters left out and sent. Ids come from other calls'
  results: a parameter called `careerId` takes the `careerId`s a read returns, and `courseId`
  the `id`s of a record named after courses.
- **responses match the spec.** The clients decode leniently, so each JSON response is also
  checked against what the spec says it looks like. Fields the spec doesn't know, values of
  another type, enum values it doesn't list and missing required fields are reported; only a
  response that doesn't decode fails the case.
- **errors are the API's.** An id no server knows must be refused or answered with nothing;
  invalid credentials, and requests without the account's headers, must be refused with the
  API's error.
- **the platforms agree.** Each case writes a fingerprint of the result it decoded, and the
  nightly summary flags the cases whose fingerprints differ between platforms.
- **changes can be undone.** A reversible operation is called, checked, and undone right away.

The values cases pick from other results change every day, so that runs cover more data over
time; the report notes the seed, which `LIVE_SEED` sets to repeat a run.

### Effects

Every operation has an effect, which decides whether tests may call it:

| Effect         | Meaning                                                              | Tests call it               |
|----------------|----------------------------------------------------------------------|-----------------------------|
| `read`         | Changes nothing anyone can see, whatever the HTTP method             | Always                      |
| `benign`       | Changes only state nobody relies on: logs, session settings, a token | Once, its inputs only from `tests.yaml` |
| `reversible`   | Changes real state that another operation undoes exactly             | With writes on, then undone |
| `irreversible` | Messages, submissions, payments, attendance, records staff act on    | Never                       |

GETs are reads unless the spec says otherwise. Other operations must say: with `x-mb-effect` in an
OpenAPI spec, or in the `effects.json` next to a spec that can't, keyed by `Module.operation`
with the reason for the choice. Moodle's own read flag counts as `read`. Generation fails for an
operation without an effect.

### tests.yaml

Most operations need nothing: the planner finds their values itself. `tests.yaml` says what it
can't: the account, and the values, checks and undos of the operations that need them.

```yaml
account:
  env: [ESSE3_USERNAME, ESSE3_PASSWORD]   # without them, the API's cases are skipped
  roles: [STUDENT]                        # operations needing other roles are skipped
  headers:
    Authorization: "Basic {base64:{env:ESSE3_USERNAME}:{env:ESSE3_PASSWORD}}"
  anonymous: [Careers.getCareers]         # also called without the headers, expecting a refusal
limits: { requestsPerSecond: 2, maxRequests: 2500, casesPerOperation: 6 }
defaults:
  courseId: { from: Course.getUsersCourses, pick: "[*].id" }   # for every input of that name
operations:
  Calendar.getMonthlyView:
    inputs: { year: "{today:yyyy}", month: "{today:MM}" }
    volatile: true                         # changes from minute to minute: don't compare platforms
  Grade.getGradeItems:
    errors: [nopermissions]                # a refusal this account may get, which passes
  Exams.book:
    undo: { call: Exams.cancel, with: { bookingId: $result.id } }
    verify: { call: Exams.getBookings, contains: { path: "[*].id", value: $result.id } }
```

| Key                        | Meaning                                                             |
|----------------------------|---------------------------------------------------------------------|
| `account.env`              | Environment variables the account needs                             |
| `account.roles`            | The roles of the API the account has                                |
| `account.headers`          | Headers every request carries                                       |
| `account.parameters`       | Values of the API parameters                                        |
| `account.auth`             | Credentials of each auth scheme: `{Scheme: {credential: value}}`    |
| `account.settings`         | Values of the client settings                                       |
| `account.anonymous`        | Operations also called without the headers, which must be refused   |
| `limits`                   | `requestsPerSecond`, `maxRequests`, `casesPerOperation`, and `negative: false` to drop the error cases |
| `defaults`                 | Values of every input of a name; optional inputs are also left out, and go without a value nothing provides |
| `operations.<op>.skip`     | Why the operation isn't tested                                      |
| `operations.<op>.inputs`   | Values of its inputs, by name (`body` for the body)                 |
| `operations.<op>.expect`   | Checks of every result: `nonEmpty`, `contains`, `equals`, `matches`, `count` |
| `operations.<op>.errors`   | Statuses and error codes it may answer with                         |
| `operations.<op>.volatile` | Whether its results change too fast to compare platforms            |
| `operations.<op>.negative` | `false` to drop its error cases                                     |
| `operations.<op>.undo`     | How to undo it: `call` another operation, or `restore` a value saved before |
| `operations.<op>.verify`   | A read showing the change, until it is undone                       |

Values are written like this:

| Value                                          | Means                                             |
|------------------------------------------------|---------------------------------------------------|
| `3`, `true`, `text`                            | That value; enums by their wire value, dates in ISO 8601 |
| `"{env:NAME}"`, `"{today+7}"`, `"{today:yyyy}"`, `"{base64:…}"` | Text the runtime fills in when the tests run |
| `null`                                         | Leave the input out                               |
| `{from: Module.op, with: {…}, pick: "[*].id", where: {active: true}}` | One of the values another call returns |
| `{oneOf: [a, b]}`                              | Each value in turn, like an enum's                |
| `{…}` or `[…]`                                 | JSON, decoded into the input's type as servers send it |
| `$args.<input>`, `$result.<path>`, `$before`   | In `undo` and `verify`: the call's arguments, its result, the saved value |

Paths walk fields by name; `[*]` is every element of a list or value of a map, and `[2]` one
element. Inputs of a call that pick from the same list of the same call take their values from
one element of it, so that a course's id and its code belong together. Mistakes, such as an
unknown operation or field or a value of the wrong type, fail generation. `--plan` prints the cases an API's `tests.yaml` leads to, and why operations are
skipped.

### Running them

| Platform   | Command                                                    | Reports                               |
|------------|------------------------------------------------------------|---------------------------------------|
| Kotlin     | `./gradlew -p data-api liveTest` (from `android/`)          | `android/data-api/build/live-reports` |
| TypeScript | `npm run test:live` (from `web/web-app/`)                  | `web/web-app/data-api/test-results/live` |
| Swift      | `LIVE_TESTS=1 swift test --filter LiveTests` (from `ios/DataApi`) | `ios/DataApi/.build/live-reports` |

Pick one API with `--tests '*.esse3.live.*'` (Kotlin), a folder such as `test/esse3` (vitest) or
`--filter LiveTests.Esse3` (Swift). The account's variables come from the environment, and so do
these:

| Variable                | Meaning                                                              |
|-------------------------|----------------------------------------------------------------------|
| `LIVE_TESTS`            | `1` to run the tests; otherwise they are skipped (Gradle and vitest set it) |
| `LIVE_WRITES`           | `1` to run the reversible cases                                      |
| `LIVE_SEED`             | Which values cases pick; changes every day by default                |
| `LIVE_REQUIRED`         | `1` to fail, rather than skip, the cases of an API whose account is missing |
| `LIVE_REPORT_DIR`, `LIVE_JOURNAL` | Where the report and the journal go                        |
| `LIVE_FINGERPRINT_TEXT` | `1` to also report the canonical form of results, values included, to compare platforms by hand |

`common/codegen/testing/report.py <reports>` summarizes the reports of every platform as Markdown.

The `Live tests` workflow runs Kotlin, then TypeScript, then Swift every night with the same
seed, with the accounts in the `ESSE3_USERNAME`, `ESSE3_PASSWORD` and `MOODLE_TOKEN` secrets,
and posts the summary. It fails when a case fails, or the platforms decode a result differently.

### Safety

- Irreversible operations are never called, and benign and reversible ones only with values
  `tests.yaml` gives: never with ids the planner picked.
- Reversible cases run only with `LIVE_WRITES=1` and an undo. The undo runs whatever the checks
  find, and the journal notes each change until it is undone, so that the next run undoes what an
  interrupted one left behind. A new reversible case stays `skip`ped until someone has watched
  it run once.
- Each run keeps to its API's request rate and budget.
- Reports hold outcomes, field names and fingerprints, never results or credentials; at most an
  enum value the spec doesn't list.

## Extending

- **New platform:** add a `targets/<id>` module with a `CodeTarget`, register it in
  `META-INF/services/it.attendance100.mybicocca.codegen.core.CodeTarget`, include it in
  `settings.gradle.kts` and as a `runtimeOnly` dependency of `cli`, then write its runtime, and
  its live tests (`generateTests` and `sharedTestFiles`) on a live test runtime of its own.
  Copying an existing target is the easiest start: they all share the same structure.
- **New spec format:** same thing, with a `SpecReader` under `readers/<id>`.
- **New resource:** declare it in the spec (see [Resources](#resources)), and add its builder to
  `resources/` as a `ResourceBuilder` listed in
  `META-INF/services/it.attendance100.mybicocca.codegen.core.ResourceBuilder`.
- **New codec:** add it to `Codec` in the model, then implement it in every target and runtime.

## Testing

```sh
../../android/gradlew test                      # every module
../../android/gradlew test -PupdateGolden=true  # accept intended changes to the generated code
```

Each target generates the sample API in `testing`, and the live tests of its `SampleTests`, and
compares them with the golden files in its `src/test/golden`, so any change to the output shows
up as a diff in review. CI also type-checks the web package and its live tests, and builds and
tests the Swift package on macOS.
